# AR-003 — Landing zone AWS: conta vendida via Account Factory, com baseline de guardrails aplicado desde o provisionamento

> **Como usar este documento:** esta referência é o que um time de entrega recebe ao solicitar uma nova conta AWS para hospedar um workload já posicionado em nuvem pela [ADR-0002](/ARC/issues/ARC-3#document-adr-0002-workload-placement-decision-framework). Ela realiza [ADR-0003](/ARC/issues/ARC-4#document-adr-0003-landing-zone-padrao-por-nuvem) (estrutura da landing zone), [ADR-0004](/ARC/issues/ARC-4#document-adr-0004-kubernetes-gerenciado-vs-openshift) (runtime de container) e [ADR-0005](/ARC/issues/ARC-4#document-adr-0005-guardrails-custo-capacidade-nuvem) (custo e capacidade) para a AWS especificamente. Ela também incorpora, como desenho vigente de trabalho e **não como decisão aprovada**, o que três ADRs ainda `proposta` do Technical Architect e do Security Architect já prescrevem para o lado AWS — gateway de API ([ADR-0010](/ARC/issues/ARC-6#document-adr-0010-api-gateway-exposure-strategy)), gestão de segredos e chaves ([ADR-0013](/ARC/issues/ARC-7#document-adr-0013-gestao-de-segredos-e-chaves-entre-os-quatro-ambientes)) e logging/trilha de auditoria ([ADR-0015](/ARC/issues/ARC-13#document-adr-0015-logging-seguranca-trilha-auditoria)) — porque tratar uma ADR `proposta` como se não existisse, quando ela já tem conteúdo endereçado ao Cloud Architect, produziria uma referência pior do que uma que declara a pendência de aceitação explicitamente. Não decide nada por si só — se faltar uma decisão para esta referência ficar completa, a lacuna é nomeada na §10, não preenchida aqui.

## 1. Quando usar esta referência — e quando não usar

**Use esta referência quando todos estes forem verdadeiros:**

- O workload já foi posicionado na AWS pelo framework de decisão da `ADR-0002` (esta AR não reabre essa decisão).
- O time precisa de uma unidade de isolamento nova (conta AWS) ou está avaliando uma conta já provisionada contra o baseline de guardrails.
- O workload roda em container, VM, ou ambos, dentro da AWS — a referência cobre as duas formas de compute.
- O tier de criticidade do workload é **Tier 2 ou Tier 3** (ver §7) — Tier 0 e Tier 1 não são hoje reivindicáveis para um workload hospedado na AWS, por regra interina de `ADR-0009` Q3/Q6.

**Não a use quando qualquer um destes for verdadeiro** (e indique a alternativa):

| Se … | Use em vez disso |
| --- | --- |
| O workload ainda não tem posicionamento decidido (DC vs. nuvem, e qual nuvem) | `ADR-0002` — fluxo de decisão de posicionamento |
| O workload é destinado ao Azure ou à OCI | `AR-004` ou `AR-005` (mesma task, [ARC-4](/ARC/issues/ARC-4)) |
| O workload roda on-premises (`DC-AA`, `OCP`, `VM-ON`) | Referências do Infrastructure Architect, [ARC-5](/ARC/issues/ARC-5) |
| O workload armazena, transmite ou processa dados de portador de cartão, ou se conecta a um sistema que o faz, e precisa de aprovação formal de enclave PCI-DSS | Esta referência fixa apenas a unidade de isolamento estrutural (§8); a aprovação do enclave é do Security Architect e **não existe hoje em nenhuma nuvem** (`ADR-0003` §9, Q1) — trate como bloqueado até essa aprovação existir |
| O workload exige Tier 0 ou Tier 1 de resiliência | Não reivindicável na AWS hoje — ver §7; aguarde `ADR-0009` Q3/Q6, ou posicione o workload no `DC-AA` |
| O time precisa de uma decisão de gateway de API para exposição externa ou de parceiro | O desenho vigente (`ADR-0010`, ainda `proposta`) já atribui essa exposição ao Axway, nunca ao `AGW-AWS` — ver §6 e §8; o Axway é do Technical Architect, [ARC-6](/ARC/issues/ARC-6) |

**Anti-padrões que esta referência existe para prevenir:**

- Provisionar uma conta AWS manualmente pela console, fora do Account Factory, "só para um teste" que depois recebe tráfego de produção.
- Misturar workloads CDE e não-CDE na mesma conta porque "é só por enquanto".
- Assumir que uma conta provisionada antes desta AR já tem o baseline de guardrails, sem verificar.
- Reivindicar Tier 0 ou Tier 1 para um workload AWS citando apenas a tabela de tiers de `ADR-0009` §4, sem verificar a regra interina de claimability em nuvem (§7).

## 2. O arquétipo de workload

Esta referência cobre a unidade estrutural (conta AWS), não uma arquitetura de aplicação específica. Serve a qualquer workload — transacional síncrono, batch, ou API exposta — posicionado na AWS sob a `ADR-0002`, nas faixas: Tier 0–3 de criticidade (escala de `ADR-0009`), mas **apenas Tier 2 e Tier 3 são claimáveis para um workload hospedado na AWS hoje** (§7); volume de transação não limitado por esta AR — os limites de capacidade são fixados por workload via quota (§6); sensibilidade de dado, de público a CDE, com a ressalva de bloqueio de CDE acima. Consumidores: interno, parceiro, público, mobile — a exposição externa e de parceiro é sempre pelo Axway (`ADR-0010` C1/C2, ainda `proposta`); o `AGW-AWS`, quando usado, serve exclusivamente exposição in-cloud (`ADR-0010` C3/C15).

## 4. Fluxos de ponta a ponta

1. **Caminho feliz:** o time de entrega abre uma solicitação de nova conta via o Account Factory (nunca pela console) → o Control Tower aplica o baseline de guardrails (SCPs, logging centralizado para a conta Log Archive, tags obrigatórias de `ADR-0005` incluindo `escopo-pci`, identidade) antes de qualquer recurso de workload ser criado → o time provisiona o workload (EKS ou VM) dentro da conta já conforme, com o piso de admissão PSA/Kyverno aplicado ao cluster (`ADR-0004` C4) e segredos/chaves geridos via AWS Secrets Manager/KMS desde o primeiro deploy (`ADR-0013`, ainda `proposta`).
2. **Caminho de falha primário:** a solicitação de conta falha a validação de guardrail (ex.: tag obrigatória ausente) → o Account Factory rejeita o provisionamento e retorna o erro ao time, sem criar uma conta parcialmente conforme. **Ressalva de ferramenta:** o Account Factory padrão do Control Tower (via console/Service Catalog) não valida tags customizadas na criação da conta — essa validação exige o AWS Control Tower Account Factory for Terraform (AFT), ou uma customização equivalente sobre o Account Factory padrão, que intercepte a solicitação antes do provisionamento. A ferramenta de vending definitiva (Terraform/AFT vs. nativa vs. combinação) é questão aberta de `ADR-0003` §9, Q3; até essa decisão, esta AR assume AFT como premissa de trabalho para a validação descrita aqui.
3. **Failover de site (conectividade híbrida AWS ↔ `DC-AA`):** esta AR não decide a topologia de conectividade híbrida — isso é `ADR-0007` (Infrastructure Architect, [ARC-5](/ARC/issues/ARC-5)), não `ADR-0003` C5 (que fixa apenas a topologia hub-and-spoke *dentro* da landing zone AWS, e diz explicitamente que a conectividade híbrida é decidida por `ADR-0007`). O fluxo real de failover híbrido — cada sítio do `DC-AA` com circuito dedicado + VPN de contingência próprios e independentes para a AWS, sem ponto único de falha de link nem de sítio — está descrito em detalhe na §7, porque é insumo direto para o tiering de DR de qualquer workload AWS com dependência on-premises. O tiering de DR em si (`ADR-0009`) permanece do Infrastructure Architect; síncrono/assíncrono e local do estado são definidos workload a workload, fora desta AR.
4. *(autenticação e segredos)* até `ADR-0012` ser aceita, a autenticação usa IAM nativo da conta AWS, sem federação formal com os demais ambientes — lacuna temporária declarada em `ADR-0003` §5 (Negativas). Para segredo de aplicação e chave de criptografia, o desenho vigente de `ADR-0013` (ainda `proposta`) já prescreve AWS KMS e AWS Secrets Manager/Parameter Store com credencial dinâmica preferencial (C5) e proibição de segredo em configuração versionada (C4) — ver §6; esse desenho é adotado como premissa de trabalho por esta AR, não como decisão aceita.

| `AWS-VM` — compute AWS | Sim | VMs (EC2) dentro da mesma estrutura de conta; sujeitas ao mesmo baseline de guardrails |
| `AZR-K8S` / `AZR-VM` | N/A | Fora desta AR — ver `AR-004` |

| `DATA-NREL` — bases de dados não relacionais | Sim | DynamoDB ou equivalente; mesma observação de guardrail pendente e de credencial dinâmica onde disponível |
| `AGW-AWS` — AWS API Gateway | Sim, com restrição | Provisionado dentro da conta **apenas para exposição in-cloud** — provider e consumer na mesma conta/região AWS, chamada que não sai da nuvem (`ADR-0010` C15). `AGW-AWS` MUST NOT ser usado como borda externa ou de parceiro (C3) — essa exposição é sempre pelo Axway, qualquer que seja o ambiente onde o provider roda (C1/C2). Quando uma API AWS é exposta externamente e já está publicada atrás do `AGW-AWS` por outro motivo, o único encadeamento permitido é Axway → `AGW-AWS` (C6), com a autenticação do consumidor externo ocorrendo exatamente uma vez, no Axway (C7). `AGW-AWS` MUST NOT transportar dado de portador de cartão até haver enclave aprovado para a landing zone AWS (C9). Este desenho é de `ADR-0010`, ainda `proposta` — adotado aqui como premissa de trabalho, não como decisão aceita |
| `AGW-AZR` / `AGW-AXW` | N/A | Fora desta AR — o Axway é borda externa/de parceiro única do banco (`ADR-0010` C1/C2), hospedado no `DC-AA`, fora do escopo estrutural desta AR |

**Divisão entre container e VM:** ambos coexistem na mesma estrutura de conta; a escolha entre EKS e EC2 puro é do time de entrega, por workload, sujeita a `ADR-0004` (nenhum OpenShift auto-gerenciado sem waiver).

**Multiplataforma:** esta AR é específica da AWS — não é uma variante entre nuvens. O padrão default dentro da AWS é conta provisionada via Account Factory com EKS para container; EC2 isolado é a variante para workloads que não precisam de orquestração.

### 6.1 Tagueamento de custo e escopo PCI — exemplo aplicado (realiza `ADR-0005` C1)

A tag `escopo-pci` e as demais tags obrigatórias de `ADR-0005` C1 não são apenas mencionadas: esta AR fixa como elas chegam ao recurso, não só à conta, na AWS especificamente. Ativar cost allocation tags na Organization torna a tag **visível no relatório de billing**, mas não **aplica** a tag a um recurso que não a tenha — por isso o vending (`ADR-0003` C6) precisa combinar:

- **AWS Organizations Tag Policies**, definindo os valores permitidos para cada tag obrigatória; e
- uma **SCP** que nega a criação de recurso sem a tag obrigatória presente, usando a chave de condição `aws:RequestTag`, como passo do Account Factory — ou, quando a granularidade por recurso não for exigida, atribuição no nível de conta via **Cost Categories**, já que a conta é a unidade de workload nesta AR.

Exemplo concreto de bloco de tags aplicado a uma conta de workload Tier 2, não CDE, provisionada por este padrão:

```
workload            = "pagamentos-boletos-api"
time-responsavel    = "squad-pagamentos"
ambiente            = "producao"
classe-criticidade  = "tier-2"
centro-de-custo     = "cc-4821"
escopo-pci          = "fora"
```

Para uma conta CDE dedicada, `escopo-pci` usa o valor `cde`; para uma conta de sistema conectado (ex.: a que hospeda o workload de orquestração administrativa descrito em §8), o valor é `conectado` — nunca um binário `sim`/`não`, porque isso perderia a distinção que o inventário de ativos do PCI-DSS exige entre CDE e sistema conectado (`ADR-0005` C1; família de requisitos afetada em §8).

### 7.2 Fluxo de failover híbrido real (realiza `ADR-0007`, Infrastructure Architect)

O fluxo de failover que uma conta AWS provisionada sob este padrão herda **não** vem de `ADR-0003` C5 — essa cláusula fixa apenas a topologia hub-and-spoke *dentro* da landing zone AWS (VPC hub + Transit Gateway) e devolve explicitamente a conectividade híbrida para `ADR-0007`. A topologia real, do Infrastructure Architect, coautorada pelo Cloud Architect, é:

1. **Dois caminhos, dois sítios, sem ponto único de falha (C1–C4).** Cada um dos dois sítios do `DC-AA` tem conectividade híbrida própria e independente para a AWS — um circuito dedicado primário (**AWS Direct Connect**) mais uma VPN de contingência com failover automático, por sítio. Nenhum sítio é o único ponto de acesso híbrido para a AWS: os dois sítios têm caminho próprio. A perda de um único circuito (dedicado ou de contingência) não interrompe a conectividade daquele sítio com a AWS — o tráfego falha automaticamente para o caminho remanescente do mesmo sítio. A perda completa de um sítio não interrompe a conectividade híbrida do sítio remanescente com a AWS.
2. **Diversidade de PoP, colocation e operadora (C8).** Dentro de um mesmo par sítio/AWS, o circuito dedicado e o caminho de contingência não podem compartilhar o mesmo ponto de presença/meet-me da AWS, o mesmo datacenter de colocation, nem a mesma operadora de telecom na última milha. Confirmado tecnicamente alcançável pelo Cloud Architect ([ARC-31](/ARC/issues/ARC-31)): há mais de uma localização de peering física para Direct Connect em São Paulo, operada por colocations/operadoras distintas — o que falta é inventariar qual localização cada circuito já contratado usa hoje (`ADR-0007` §9 Q4, 30 dias corridos após a vigência).
3. **Capacidade do sítio remanescente (C9).** Na perda completa de um sítio, os circuitos do sítio remanescente para a AWS devem ter capacidade para absorver 100% do tráfego híbrido daquela nuvem — isto é topologia fixada por `ADR-0007`, não uma recomendação de dimensionamento que esta AR decida isoladamente. Onde a VPN de contingência não sustentar a carga completa (teto típico de ~1,25 Gbps por túnel gerenciado, `ADR-0007` §9 Q5), a perda do circuito dedicado é tratada como cenário de degradação explícito, não como continuidade plena.
4. **Roteamento pós-failover (C10).** Tráfego originado na AWS que escreve em um domínio de dado cujo primário é on-premises é roteado para o sítio do `DC-AA` que hospeda o primário daquele domínio no momento, e é re-roteado automaticamente após um evento de failover controlado de `ADR-0006`. Firewalls stateful em cada sítio não podem descartar o tráfego de retorno após o re-roteamento.
5. **Criptografia para caminho CDE (C11).** Todo caminho híbrido que carregar ou puder carregar dado de CDE — dedicado ou de contingência — usa IPsec como mecanismo padrão de criptografia forte em trânsito (família de requisito na linha `OBL-PCI` de §8); a identificação de quais caminhos carregam dado de CDE é do Security Architect (`ADR-0014` §5, prazo de 45 dias) — até então, C11 é tratada por precaução como aplicável a todo caminho que possa carregar dado de CDE.
6. **RTT ainda não medido — interliga diretamente com a claimability de tier (§7.1).** O RTT entre a AWS e o `DC-AA`, por sítio/caminho, e o objetivo de restauração de uma partição híbrida total (alvo de trabalho RTO ≤ 4h, não capacidade comprovada) estão sob medição, prazo de 90 dias corridos após a vigência de `ADR-0009`, mesma data da confirmação de capacidade de failover em nuvem citada em §7.1 (`ADR-0007` §3.2/§9 Q8, decisão D-8 do Arquiteto Principal). Até essa confirmação, nenhum desenho que dependa de um provider em nuvem para Tier 0/1 pode reivindicar esse tier — o que é consistente com, e reforça, a regra de §7.1.

**Fluxo 3 — limite de transação e natureza síncrona/assíncrona (R8):** o próprio failover de site não é, em si, uma transação de negócio com limite de valor — é um evento de roteamento de infraestrutura. O que R8 exige aqui é declarado para o tráfego que esse fluxo redireciona: a escrita de uma transação cujo domínio primário é on-premises é **síncrona** até o ponto de confirmação (o workload em nuvem aguarda o ack do primário on-premises antes de confirmar ao consumidor, sem limite de valor de transação imposto por este fluxo — o limite, quando existir, é de `ADR-0011`, por domínio de dado, não desta AR); durante a janela de failover controlado de `ADR-0006`, a escrita é pausada no domínio afetado até a promoção concluir, nunca atendida de forma assíncrona ou "best effort" sem confirmação.

## 11. Notas de custo e capacidade

Direcionadores de custo na AWS: taxa de control plane do EKS por cluster-hora — **USD 0,10/hora/cluster, ≈ USD 876/ano/cluster** (preço de lista público na data de `ADR-0004` §4.1, custo recorrente mesmo sem nó ativo); compute EC2/nós EKS conforme instância e savings plan avaliado para consumo estável (`ADR-0005` C5); transferência de dados entre AZs e entre `sa-east-1` e outras regiões, incluindo tráfego pelo Transit Gateway e pelos circuitos Direct Connect para o `DC-AA` (`ADR-0007`); chamadas de AWS API Gateway, quando usado para exposição in-cloud, cobradas por requisição — quota de taxa é obrigatória (`ADR-0005` C3).

**Modelo de custo comparativo de runtime (`ADR-0004` §4.4):** os números abaixo foram conferidos contra o texto vigente de `ADR-0004` §4.4 nesta revisão, para evitar divergência entre documentos; a fonte autoritativa do modelo de custo é `ADR-0004`, não esta AR. Nos três cenários de volume (Baixo = 8 clusters, Base = 14, Alto = 28, mix proporcional AWS/Azure/OCI 6/5/3), a Opção B (Kubernetes gerenciado nativo, escolhida — EKS na AWS) custa, em 3 anos: **≈ USD 161.000 (Baixo) / ≈ USD 188.000 (Base) / ≈ USD 250.000 (Alto)**. A Opção A (OpenShift auto-gerenciado em todas as nuvens) custa **≈ USD 464.000 / ≈ USD 610.000 / ≈ USD 950.000** nos mesmos cenários — razão A/B entre **≈ 2,9× e ≈ 3,8×**. O misto "ROSA/ARO nos clusters AWS/Azure + Kubernetes gerenciado na OCI" custa entre **≈ 2,5× e ≈ 4,6×** mais que a Opção B pura (≈ 2,0×–3,3× na sensibilidade sem as VMs de control plane do ARO). Para a AWS especificamente, o custo por cluster em 3 anos do ROSA HCP é **≈ USD 33.500**, contra o custo de EKS puro (control plane + compute, sem licenciamento Red Hat) — a diferença é o que justifica EKS como padrão (C1) e ROSA como exceção por aplicação apenas quando a lacuna de equivalência SCC↔PSA/Kyverno (C4/C7) o exigir, nunca por custo.

**Custo de guardrail de tagueamento e budget:** o esquema de tag comum (§6.1) e o par SCP/Tag Policies não têm custo de licença direto na AWS; o custo real é de engenharia única de configuração do Account Factory/AFT e de manutenção contínua do esquema sincronizado entre as três nuvens (`ADR-0005` §3, Opção C). Penhasco conhecido: o Account Factory e o Control Tower em si não têm custo direto de licença, mas o volume de contas cresce o custo de CloudTrail/Config agregado centralmente na conta Log Archive — ordem de grandeza detalhada depende do volume de contas do primeiro ano, ainda não confirmado (`ADR-0003` §9 Q3/Q4).

## 12. Orientação sobre desvios

- Desviar de uma cláusula `SHOULD` (ex.: `ADR-0003` C5, topologia hub-and-spoke intra-landing-zone; `ADR-0010` C13, baseline de borda): registre localmente, sem waiver.
- Desviar de uma cláusula `MUST` de uma ADR já realizada por esta AR (`ADR-0003` C1–C4, C6, C7; `ADR-0004` C1, C3, C4; `ADR-0005` C1–C4): waiver necessário — ver o [processo de exceção e waiver](/ARC/issues/ARC-2#document-exception-and-waiver-path).
- Desviar do desenho incorporado de uma ADR ainda `proposta` (`ADR-0007` C1–C4, C8–C11; `ADR-0010` C1–C3, C6, C7, C9, C15; `ADR-0012` C10; `ADR-0013` C1–C5; `ADR-0014` C2; `ADR-0015` C2, C4–C7, C14): registre o desvio da mesma forma (localmente para `SHOULD`, waiver para `MUST`/`MUST NOT`) **enquanto o desenho vale como premissa de trabalho desta AR**, deixando explícito que a cláusula de origem ainda depende da própria ADR ser aceita pelo comitê — o waiver, se concedido, vale contra o desenho adotado por esta AR, não contra uma ADR aceita.
- Encontrou um caso que esta referência não cobre? Levante uma pergunta de intake (modelo operacional §5, Etapa 1).
