# AR-004 — Landing zone Azure: subscription vendida sob hierarquia de management groups, com baseline de guardrails aplicado desde o provisionamento

> **Como usar este documento:** esta referência é o que um time de entrega recebe ao solicitar uma nova subscription Azure para hospedar um workload já posicionado em nuvem pela [ADR-0002](/ARC/issues/ARC-3#document-adr-0002-workload-placement-decision-framework). Ela realiza [ADR-0003](/ARC/issues/ARC-4#document-adr-0003-landing-zone-padrao-por-nuvem) (estrutura da landing zone), [ADR-0004](/ARC/issues/ARC-4#document-adr-0004-kubernetes-gerenciado-vs-openshift) (runtime de container) e [ADR-0005](/ARC/issues/ARC-4#document-adr-0005-guardrails-custo-capacidade-nuvem) (custo e capacidade) para o Azure especificamente. Ela também **consome**, para o Azure, o que já está prescrito por [ADR-0007](/ARC/issues/ARC-5#document-adr-0007-conectividade-hibrida) (conectividade híbrida, Infrastructure Architect), [ADR-0009](/ARC/issues/ARC-5#document-adr-0009-tiering-de-dr) (tiering de DR, Infrastructure Architect), [ADR-0010](/ARC/issues/ARC-6#document-adr-0010-api-gateway-exposure-strategy) (gateway, Technical Architect), [ADR-0013](/ARC/issues/ARC-7#document-adr-0013-gestao-de-segredos-e-chaves-entre-os-quatro-ambientes) (segredos e chaves, Security Architect) e [ADR-0015](/ARC/issues/ARC-13#document-adr-0015-logging-seguranca-trilha-auditoria) (auditoria, Security Architect). Todas as cinco permanecem `proposta` — nada neste documento transcreve conteúdo delas como aceito; onde esta AR usa seu conteúdo, a tabela de cabeçalho e as seções correspondentes marcam explicitamente "Realiza" (estrutura que já existe no texto da ADR) versus "Decisões ainda `proposta`" (não aprovadas, sujeitas a mudar sem aviso a esta AR). Não decide nada por si só — se faltar uma decisão para esta referência ficar completa, a lacuna é nomeada na §10, não preenchida aqui.

## 1. Quando usar esta referência — e quando não usar

**Use esta referência quando todos estes forem verdadeiros:**

- O workload já foi posicionado no Azure pelo framework de decisão da `ADR-0002` (esta AR não reabre essa decisão).
- O time precisa de uma unidade de isolamento nova (subscription Azure) ou está avaliando uma subscription já provisionada contra o baseline de guardrails.
- O workload roda em container, VM, ou ambos, dentro do Azure — a referência cobre as duas formas de compute.

**Não a use quando qualquer um destes for verdadeiro** (e indique a alternativa):

| Se … | Use em vez disso |
| --- | --- |
| O workload ainda não tem posicionamento decidido (DC vs. nuvem, e qual nuvem) | `ADR-0002` — fluxo de decisão de posicionamento |
| O workload é destinado à AWS ou à OCI | `AR-003` ou `AR-005` (mesma task, [ARC-4](/ARC/issues/ARC-4)) |
| O workload roda on-premises (`DC-AA`, `OCP`, `VM-ON`) | Referências do Infrastructure Architect, [ARC-5](/ARC/issues/ARC-5) |
| O workload armazena, transmite ou processa dados de portador de cartão, ou se conecta a um sistema que o faz, e precisa de aprovação formal de enclave PCI-DSS | Esta referência fixa apenas a unidade de isolamento estrutural (§8); a aprovação do enclave é do Security Architect e **não existe hoje em nenhuma nuvem** (`ADR-0003` §9, Q1) — trate como bloqueado até essa aprovação existir |
| O time precisa de uma decisão de gateway de API | `ADR-0010` ([ARC-6](/ARC/issues/ARC-6)), ainda `proposta` — ver §6; esta AR descreve o que `ADR-0010` já prescreve para o Azure, mas não a aprova |

**Anti-padrões que esta referência existe para prevenir:**

- Provisionar uma subscription Azure manualmente pelo portal, fora do processo de vending, "só para um teste" que depois recebe tráfego de produção.
- Misturar workloads CDE e não-CDE na mesma subscription porque "é só por enquanto".
- Assumir que uma subscription provisionada antes desta AR já tem o baseline de guardrails, sem verificar.
- Assumir que, por o accelerator ter criado a subscription, as tags obrigatórias (`ADR-0005` C1) já foram validadas — essa validação é do **pipeline de vending de subscription**, não do accelerator (ver §4, §5, §9).

## 2. O arquétipo de workload

Esta referência cobre a unidade estrutural (subscription Azure), não uma arquitetura de aplicação específica. Serve a qualquer workload — transacional síncrono, batch, ou API exposta — posicionado no Azure sob a `ADR-0002`, nas faixas: Tier 0–3 de criticidade (escala de `ADR-0009`; tiering formal pendente de `ADR-0009` alcançar `aceita`, autodeclarado até então, conforme `ADR-0005` C1). **Tier 0 e Tier 1 não são reivindicáveis hoje para workload posicionado no Azure** — ver §7. Volume de transação não limitado por esta AR — os limites de capacidade são fixados por workload via quota (§6); sensibilidade de dado, de público a CDE, com a ressalva de bloqueio de CDE acima. Consumidores: interno, parceiro, público, mobile — a exposição externa segue sempre o Axway como borda (`ADR-0010`, `proposta` — ver §6).

## 4. Fluxos de ponta a ponta

1. **Caminho feliz:** o time de entrega abre uma solicitação de nova subscription via o landing zone accelerator (nunca pelo portal) → o accelerator aplica o scaffolding inicial (estrutura, política base) → o **pipeline de vending de subscription** valida as tags obrigatórias de `ADR-0005` (incluindo `escopo-pci`), o logging centralizado e a identidade, e só então libera a subscription → o time provisiona o workload (AKS, ARO por aprovação conjunta Cloud Architect + Security Architect — C7, D-22(k) —, ou VM) dentro da subscription já conforme.
2. **Caminho de falha primário:** a solicitação de subscription falha a validação de guardrail (ex.: tag obrigatória ausente) **no pipeline de vending de subscription** — não no accelerator, que não valida tag — e o pipeline rejeita o provisionamento, sem liberar uma subscription parcialmente conforme para recursos de workload.
3. **Failover de site:** o fluxo real de conectividade híbrida entre o `DC-AA` e o Azure é o de `ADR-0007` (Infrastructure Architect, co-autorado com o Cloud Architect), não uma invenção desta AR: cada um dos dois sites do `DC-AA` tem, para o Azure, um circuito dedicado primário (ExpressRoute) e uma VPN de contingência independentes, com failover automático (`ADR-0007` C1); a perda de um único circuito falha para o caminho remanescente do mesmo site (C3); a perda de um site inteiro não isola o Azure, porque o outro site tem seu próprio caminho íntegro (C2/C4); o site remanescente precisa ter capacidade para absorver 100% do tráfego híbrido daquela nuvem (C9). O tiering de DR (RTO/RPO por tier) é `ADR-0009` — ver §7, inclusive a regra de que Tier 0/1 não é reivindicável hoje para workload Azure.
4. *(autenticação)* até `ADR-0012` ser aceita, a autenticação usa Microsoft Entra ID nativo da subscription, sem federação formal com os demais ambientes — lacuna temporária declarada em `ADR-0003` §5 (Negativas). Segredo de aplicação e chave de criptografia seguem `ADR-0013` (`proposta`, Decisões ainda `proposta`) — ver §6.

| Plataforma | Nesta referência? | O que você implanta / como difere aqui |
| --- | --- | --- |

| `OCP` — OpenShift on-prem | Não | Fora de escopo |
| `VM-ON` — VMs / bare metal on-prem | Não | Fora de escopo |
| `AWS-K8S` / `AWS-VM` | N/A | Fora desta AR — ver `AR-003` |
| `AZR-K8S` — Kubernetes gerenciado no Azure | Sim | AKS como runtime padrão (`ADR-0004` C1). Baseline de admissão obrigatório antes de qualquer workload Tier 1: Pod Security Admission `restricted` + Kyverno (ou OPA Gatekeeper) em `enforce`/`deny`, nunca apenas `audit`/`warn` (`ADR-0004` C4, piso do Security Architect, [ARC-33](/ARC/issues/ARC-33)) — a cláusula só se considera atendida com a matriz SCC → PSA/Kyverno, por nuvem, assinada pelo Security Architect. Nenhum cluster OpenShift auto-gerenciado sem waiver nomeado (C2/C6) |
| `AZR-VM` — compute Azure | Sim | VMs (Azure VMs) dentro da mesma estrutura de subscription; sujeitas ao mesmo baseline de guardrails |
| `OCI-K8S` / `OCI-VM` | N/A | Fora desta AR — ver `AR-005` |
| `DATA-REL` — bases de dados relacionais | Sim | Azure SQL/PostgreSQL gerenciado dentro da subscription do workload; guardrail de persistência específico é `ADR-0011` ([ARC-6](/ARC/issues/ARC-6), Technical Architect, `proposta`). Credencial de aplicação para o banco deve preferir credencial dinâmica de curta duração emitida pelo Key Vault, sobre usuário/senha estático (`ADR-0013` C5, `proposta`) |
| `DATA-NREL` — bases de dados não relacionais | Sim | Cosmos DB ou equivalente; mesma observação de guardrail pendente (`ADR-0011`) e de credencial dinâmica onde disponível (`ADR-0013` C5) |
| `AGW-AZR` — Azure API Management | Sim, restrito | Provisionado dentro da subscription **apenas para exposição in-cloud** — provider e consumer no mesmo provedor e na mesma região (`ADR-0010` C15, `proposta` — Decisões ainda `proposta`, não aceitas). **Proibido** como borda externa ou de parceiro (`ADR-0010` C3, MUST NOT); essa borda é sempre o Axway, inclusive para provider em Azure (C1/C2), podendo ocupar o segundo salto de um encadeamento único Axway → APIM quando o workload já estiver publicado atrás do APIM por outro motivo (C6). Fora do CDE até haver enclave aprovado para a landing zone Azure (C9) — a escolha de gateway em si não é desta AR |
| `AGW-AWS` / `AGW-AXW` | N/A | Fora desta AR |

**Divisão entre container e VM:** ambos coexistem na mesma estrutura de subscription; a escolha entre AKS, ARO (por aprovação conjunta Cloud Architect + Security Architect, C7, D-22(k), sem waiver formal) e VM pura é do time de entrega, por workload, sujeita a `ADR-0004` (nenhum OpenShift auto-gerenciado sem waiver fora de C7).

**Multiplataforma:** esta AR é específica do Azure — não é uma variante entre nuvens. O padrão default dentro do Azure é subscription provisionada via landing zone accelerator com AKS para container; VM isolada é a variante para workloads que não precisam de orquestração; ARO é a alternativa nomeada por aplicação (C7).

## 11. Notas de custo e capacidade

Direcionadores de custo no Azure: AKS não cobra taxa de control plane no tier gratuito, mas o tier com SLA garantido (Uptime SLA) é pago por cluster — a escolha entre os dois tiers deve ser declarada por workload conforme criticidade (`ADR-0004` C1a); compute de nós AKS/VM conforme série de instância e reserved instances avaliadas para consumo estável (`ADR-0005` C5); transferência de dados entre zonas de disponibilidade e entre `Brazil South` e outras regiões, incluindo tráfego pelo Virtual WAN para o `DC-AA`; chamadas de Azure API Management, restritas a exposição in-cloud (`ADR-0010` C15, `proposta`), cobradas por capacidade de unidade provisionada ou por volume no tier consumo — quota de taxa é obrigatória (`ADR-0005` C3). Penhasco conhecido: o número de management groups e subscriptions sob um único tenant tem limites de escala documentados pela Microsoft que devem ser monitorados conforme o número de unidades crescer.

**Comparação quantificada AKS vs. ARO (`ADR-0004` §4.1/§4.4), citada aqui exatamente como modelada**: para o mix proporcional AWS/Azure/OCI (6/5/3) do primeiro ano, em três cenários de volume (Baixo: 8 clusters; Base: 14 clusters; Alto: 28 clusters), o custo total projetado em 3 anos é — Opção A (OpenShift auto-gerenciado em todas as nuvens): ≈ USD 464.000 / ≈ USD 610.000 / ≈ USD 950.000. Opção B (Kubernetes gerenciado nativo — AKS no Azure, escolhida por `ADR-0004`): ≈ USD 161.000 / ≈ USD 188.000 / ≈ USD 250.000. A razão A/B fica entre ≈ 2,9× e ≈ 3,8×; a razão do misto "ROSA/ARO + Kubernetes gerenciado na OCI" sobre B pura fica entre ≈ 2,5× e ≈ 4,6× (≈ 2,0×–3,3× na sensibilidade sem as VMs de control plane do ARO). Esses números — não uma ordem de grandeza aproximada diferente — são os que sustentam a escolha de AKS como padrão e de ARO como alternativa por aplicação (C7), não por custo, nesta AR.

Ordem de grandeza detalhada do volume real de clusters depende do inventário do primeiro ano, ainda a confirmar (`ADR-0004` §5.3).

## 12. Orientação sobre desvios

- **Escolha de topologia de rede — por que Virtual WAN, não Hub VNet.** `ADR-0003` C5 deixa a topologia intra-nuvem como `SHOULD` e cita "Azure Virtual WAN ou hub VNet" como opções nativas equivalentes para hub-and-spoke dentro do Azure. Esta AR fixa **Virtual WAN** como a topologia única do Azure, não como complemento ao Hub VNet: o banco opera em ambiente multi-região, híbrido e active-active, com conectividade simultânea a três nuvens e ao `DC-AA` por dois sites independentes (`ADR-0007`), e o Virtual WAN entrega conectividade any-to-any entre múltiplos spokes e regiões, e simplifica a gestão de conectividade híbrida em escala, de um jeito que um Hub VNet avulso — por natureza regional, sem recursos de trânsito global — não entrega sem replicar hubs manualmente por região. Hub VNet permanece uma alternativa válida apenas para uma topologia de região única e sem necessidade de trânsito global; um time que precise dela para um caso concreto registra o desvio como abaixo (cláusula `SHOULD`, sem waiver), nunca como uma segunda topologia padrão desta AR.
- Desviar de uma cláusula `SHOULD` (ex.: `ADR-0003` C5 — usar Hub VNet em vez de Virtual WAN para um caso de topologia simples e de região única): registre localmente, sem waiver.
- Desviar de uma cláusula `MUST` (ex.: `ADR-0003` C1–C4, C6, C7; `ADR-0004` C1, C3, C4; `ADR-0005` C1–C4; `ADR-0007` C1–C4, C8–C11, quando aplicável ao lado Azure; `ADR-0013` C1–C4, C6 quando `ADR-0013` for aceita): waiver necessário — ver o [processo de exceção e waiver](/ARC/issues/ARC-2#document-exception-and-waiver-path).
- Encontrou um caso que esta referência não cobre? Levante uma pergunta de intake (modelo operacional §5, Etapa 1).
